# Архитектура рабочего пакета

Текущая реализация находится в qr_transfer/. Обзор исследований и прототипов:
[discover](https://github.com/BigZet/qr-transfer/tree/discover).

## Поток данных

1. `pack`: файл/каталог → сжатый парольный контейнер с манифестом → descriptor.json.
2. `render`: проверка контейнера → пакеты транспорта → QR-матрицы → HTML и порции.
3. Браузер JupyterHub загружает порции, проверяет CRC и рисует один/два QR.
4. `capture`: ограниченная очередь снимков → декодирование → журнал приёмника.
5. После SHA-256 архива `unpack` проверяет пароль и манифест, извлекает данные.

## Компоненты

| Модуль | Назначение |
|---|---|
| container.py | 7z, пароль, манифест, ограничения распаковки |
| protocol.py, transfer.py | Формат AQR2 и пакетирование repeat |
| storage.py | Журнал repeat, блокировка и возобновление |
| fec.py | Экспериментальный LT и его журнал |
| player.py, generation.py | QR-матрицы, пул процессов, публикация порций |
| assets/ | HTML/Canvas-плеер, ограниченный кэш и управление |
| pipeline.py, capture.py | Захват экрана, очередь, статистика и диагностика |
| rgb.py | Калибровка и разделение цветовых слоёв |
| cli.py | Команды отправителя/приёмника |

## Контракты

Сохранены форматы и совместимость с последней исследовательской реализацией.
Новый render создаёт новый transfer ID; resume допустим для прежнего ID/транспорта.
Проверка CRC пакета не заменяет проверку SHA-256 всего архива. Распаковка начинается
после подтверждения архива; пароль не записывается в HTML и отчёты.

Спецификации: [AQR2](docs/specs/aqr2.md), [LT](docs/specs/aqr2-lt.md),
[контейнер](docs/specs/container.md), [состояние](docs/specs/receiver-state.md),
[моно](docs/specs/mono-player.md), [цвет](docs/specs/rgb-qr.md),
[порционный плеер](docs/specs/paged-player.md).

Изолированный HTML на /files/ может не читать соседние файлы. Рабочий маршрут
на проверенном VDI — локальный HTTP-сервер через аутентифицированный Jupyter proxy.
Необходимо держать терминалы генератора и HTTP-сервера работающими во время передачи.
