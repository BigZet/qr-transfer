# QR Transfer — проект передачи файлов через экран VDI

Статус: проект развития существующего прототипа. Описанные ниже новые функции ещё не реализованы.

## 1. Цель

Передавать файл или каталог из окружения JupyterHub, открытого в браузере на VDI, на хост через последовательность визуальных кодов на экране, без файлового или сетевого канала между отправителем и приёмником. QR — существующий базовый формат, но не обязательное ограничение: допускаются цветные матричные коды, включая cimbar.

Целевой процесс:

1. Пользователь запускает отправитель в окружении JupyterHub — например, из терминала или ячейки — указывает доступный Python-процессу путь и задаёт пароль.
2. Отправитель создаёт архив с сильным сжатием и шифрованием.
3. Делит байты зашифрованного архива на нумерованные пакеты.
4. Браузерный плеер показывает один или несколько визуальных кодов. Пакетный режим повторяет цикл; формат с восстанавливающими кодами может генерировать новые восстановительные блоки.
5. Приёмник на хосте захватывает экран, проверяет пакеты и сохраняет новые чанки.
6. После получения всех частей проверяет размер и хеш архива, запрашивает пароль и распаковывает содержимое.

Основная метрика — время до полного восстановления исходных данных. Скорость смены кадров и количество QR сами по себе не определяют полезную пропускную способность.

## 2. Ограничения и приоритеты

- **Основная среда запуска — JupyterHub, доступный в браузере на VDI.** Notebook не обязателен. Python выполняется в пользовательском окружении JupyterHub, а анимация — в браузере. Отдельное нативное окно отправителя не требуется.
- **Python 3.10 — основная целевая версия**, 3.12 — дополнительная. Код и выбранные версии библиотек должны поддерживать 3.10.
- **Компактный отправитель — обязательное требование.** Код сложно переносить в удалённое окружение. Небольшой Python-скрипт плюс компактный HTML/JavaScript; запуск через ячейку может поддерживаться дополнительно.
- На VDI доступна копия PyPI: установка через pip предположительно возможна. Наличие конкретных пакетов, версий, транзитивных зависимостей и подходящих wheels нужно проверить в выбранном Python-окружении JupyterHub.
- Раздельно учитывать вручную переносимый код, зависимости из внутреннего PyPI и внешние ресурсы, отсутствующие в зеркале. Большая библиотека из доступного зеркала допустима, если она существенно сокращает ручной перенос.
- **Основной ориентир: 1920×1080.** 3840×2160 — дополнительный профиль. Работоспособность не должна зависеть от наличия 4K.
- Размер QR рассчитывается по реально доступной области показа и пикселям захваченного изображения; учитываются масштаб ОС, браузера и VDI-клиента.
- Канал односторонний. Автоматического подтверждения доставки или запроса пропусков от хоста нет.
- Приёмник может быть существенно сложнее отправителя: диагностика, несколько декодеров, калибровка цвета, сохранение состояния и измерения выполняются на хосте.
- Парольная защита обязательна для целевого рабочего режима.
- Несколько QR, цветность и сравнение с cimbar входят в план. Выбор основного визуального формата определяется измерениями и доступностью реализации в JupyterHub.

Порядок приоритетов: корректное восстановление и парольная защита → компактная поставка → максимальная измеренная скорость → удобство.

## 3. Что уже реализовано

Имена файлов сейчас расходятся с первоначальным описанием ролей. Ниже приведено фактическое поведение исходников; переименование этим документом не выполняется.

| Компонент | Файл сейчас | Реализация |
| --- | --- | --- |
| Отправитель, будущий компактный QR-скрипт | `code.py` | Файл/каталог → пакеты → PNG → автономный HTML |
| Приёмник | `qr.py` | Захват монитора через `mss`, распознавание через `zxingcpp`, сборка файла |

### Отправитель

- Каталог упаковывается в `tar.xz`, `preset=9`; исключаются `.git`, `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ipynb_checkpoints`.
- Обычный файл передаётся как есть, без дополнительного сжатия.
- Используется QR Model 2, версия 40, коррекция L, тихая зона 4 модуля.
- Полезный чанк по умолчанию — 2800 байт; CLI допускает 100–2850 байт.
- HTML показывает один QR, циклически повторяет кадры и вставляет метаданные примерно через каждые 8 пакетов данных.
- Интервал по умолчанию — 600 мс; минимальный разрешённый — 150 мс.
- Есть пауза, пошаговая навигация и изменение скорости с клавиатуры.
- Все PNG и итоговый HTML готовятся в памяти; изображения в HTML представлены Base64. Содержимое QR при этом бинарное, без Base64.
- При стандартном `box_size=6` PNG имеет сторону 1110 пикселей, а CSS масштабирует его до `90vmin`. На Full HD это может давать дробный размер модуля.

### Приёмник

- Захватывает весь выбранный монитор; по умолчанию `--fps=12`, таймаут 300 секунд.
- `read_barcode` обрабатывает один результат за снимок.
- Проверяет CRC32 полезной нагрузки каждого пакета; хранит уникальные чанки в оперативной памяти.
- После сборки проверяет размер и SHA-256 и записывает файл.
- Реальная частота захвата ниже заданного FPS: к задержке `1 / fps` добавляется время захвата и декодирования.

### Чего пока нет

Шифрования и ввода пароля, автоматической распаковки, нескольких QR в одном кадре, цветного режима, возобновления после перезапуска, ограничения области захвата и измеренной статистики пропускной способности. Текущий приёмник может перезаписать существующий файл с тем же именем.

## 4. Целевая архитектура

```text
Пользовательское окружение JupyterHub (Python 3.10: скрипт или ядро)
Файл/каталог → сжатие + шифрование → архив → выбранный транспорт
                                                   │
                           подготовленные данные/кадры → браузерный плеер
                                                   ↓
Браузер на VDI: HTML/JS-плеер → QR / RGB-QR / cimbar
                                                   │
                                            изображение VDI
                                                   ↓
Хост: захват → декодер формата → сборка → проверенный архив → распаковка
```

Отправитель не знает, какие данные приняты. Он продолжает показ до ручной остановки. Приёмник допускает подключение посреди передачи, пропуски, дубликаты и произвольный порядок блоков. Соединение браузера с JupyterHub — часть среды отправителя, а не обратный канал от хоста. Файловая система пользовательского окружения JupyterHub может отличаться от файловой системы рабочего стола VDI.

### Работа в JupyterHub

- Интерфейс запуска: Python-скрипт с путём, профилем и интервалом, запускаемый через доступный терминал JupyterHub, либо вызов той же функции из ячейки. Ни наличие notebook, ни наличие терминала не считать обязательным без проверки конкретной конфигурации.
- Упаковка и начальная генерация выполняются в Python-процессе. После подготовки JavaScript управляет показом локально в браузере. При запуске из ячейки не отправлять каждый следующий кадр отдельным выводом через `display`/`clear_output`.
- Плеер — отдельный HTML/JS-интерфейс с кнопками запуска, паузы и полноэкранного режима. Способ открытия выбрать из доступных средств JupyterHub: отдельная страница, разрешённый файловый маршрут либо встроенный вывод. Проверить выполнение активного HTML, CSP и разрешения iframe: файловый просмотр может ограничивать скрипты. Возможность скачать HTML на хост не предполагается.
- Встраивание в notebook — дополнительная интеграция. Для неё отдельно проверить доверие выводу и выполнение JavaScript в фактическом frontend. Сам по себе `display(HTML(...))` не гарантирует работу скриптов во всех конфигурациях.
- Для полноэкранного режима предусмотреть явное нажатие пользователем. Если он недоступен, использовать фактические размеры области вывода и уменьшить профиль.
- Для первой версии заранее передавать в плеер подготовленный набор кадров/матриц. Для больших файлов измерить время доставки в браузер и память; при запуске из notebook — также лимиты вывода и размер сохранённого документа. При необходимости добавить ограниченную буферизацию.
- Не сохранять пароль в исходнике, аргументах командной строки, журналах или HTML; при использовании notebook — также в ячейках и метаданных. Использовать скрытый ввод, работающий в выбранном интерфейсе запуска.
- Остановка и повторный запуск должны освобождать прежние таймеры и ресурсы плеера. После перезагрузки страницы или перезапуска Python-процесса возможен повторный старт из сохранённого зашифрованного архива.

Правила доверия к активному выводу описаны в [документации безопасности Jupyter Server](https://jupyter-server.readthedocs.io/en/latest/operators/security.html). Необходимые разрешения проверяются в существующей конфигурации, без отключения её защит.

## 5. Компактная поставка отправителя

Предлагаемый бюджет первой рабочей версии: **до 20 КиБ вручную переносимого UTF-8 исходника**, включая собственный HTML/JavaScript и код запуска, без библиотек из внутреннего PyPI. Это проектная цель, а не установленный пользователем численный предел. Внешний WASM/JS-бандл, если его нужно переносить вручную, учитывается дополнительно и не скрывается за размером Python-обёртки.

Подход:

- Один Python-скрипт с CLI и вызываемой функцией для необязательной интеграции с ячейкой; не переносить приёмник и средства тестирования на VDI.
- Для QR сохранить Python `qrcode` и Pillow, уже используемые прототипом; проверить совместимые с Python 3.10 версии в зеркале.
- Использовать установленный архиватор для сжатия и парольной защиты, если он доступен.
- Генерировать плеер без CDN и внешних запросов; использовать существующий JupyterHub, без отдельного устанавливаемого веб-сервера. Допускается однократная установка зависимостей из внутреннего PyPI.
- Не включать собственную реализацию QR или криптографии ради формальной автономности.
- Сначала компактный понятный код. Автоматическое уменьшение размера допустимо только при проверке эквивалентности исходной и поставляемой версии.
- Измерять время подготовки, объём HTML и пиковую память. При росте файлов перейти к ограниченному кэшу кадров или компактному представлению QR-матриц; не делать это обязательным усложнением первой версии.

Устанавливать библиотеки в выбранное окружение Python 3.10 через `python -m pip` из терминала, используя настроенное внутреннее зеркало и проверив версию интерпретатора. При работе из IPython-ячейки использовать `%pip`, предназначенный для текущего ядра: [документация IPython](https://ipython.readthedocs.io/en/stable/interactive/magics.html#magic-pip). После установки при необходимости перезапустить процесс/ядро. Не подставлять внешний PyPI как автоматический резервный источник.

Зафиксировать проверенные версии зависимостей для Python 3.10; отдельно проверить 3.12. Наличие зеркала PyPI не означает наличие системного архиватора, компилятора C++ или готового WASM. Для зависимостей с нативным кодом сначала проверить wheels под ОС/архитектуру Python-окружения.

## 6. Сжатие и парольная защита

Целевой контейнер при доступности подходящей реализации: архив `7z`, LZMA2 с максимальным выбранным уровнем сжатия, AES-256 и шифрование имён файлов. Поддержка LZMA2 и AES-256 описана в [официальной документации 7-Zip](https://www.7-zip.org/). Для JupyterHub сначала проверить Python-библиотеку работы с парольным 7z из зеркала (кандидат — `py7zr`, версия и зависимости для 3.10 ещё не выбраны); установленный 7-Zip CLI — альтернативный путь, а не обязательное условие.

- Сжимать весь вход до разделения на чанки; затем передавать байты зашифрованного архива. Независимое сжатие каждого чанка ухудшает использование повторяющихся данных.
- Обрабатывать и файлы, и каталоги. Пустые файлы должны поддерживаться.
- «Максимальное сжатие» означает сильный выбранный профиль в пределах памяти VDI. Универсально лучшего алгоритма для всех файлов нет; уже сжатые данные могут почти не уменьшиться.
- Пароль вводится скрыто, не включается в HTML, QR, журнал или рекомендуемые команды запуска. При вызове архиватора использовать поддерживаемый интерактивный ввод; конкретную интеграцию проверить на целевой ОС.
- Пароль задаётся отдельно на хосте. Передавать его тем же QR-потоком нельзя.
- Открытые метаданные содержат технический идентификатор, размер и хеш зашифрованного архива; исходные имена остаются внутри зашифрованного контейнера.
- CRC32 и SHA-256 обнаруживают ошибки передачи, но не подтверждают авторство данных. Обычный парольный 7z не следует описывать как AEAD-контейнер с криптографической аутентификацией всего протокола.
- Если 7-Zip недоступен, возможен отдельный профиль: `tar.xz` плюс парольное аутентифицированное шифрование библиотекой. Формат, KDF, соль и nonce необходимо специфицировать отдельно; это дополнительная зависимость, а не уже реализованный резервный путь.

Приёмник распаковывает только полностью проверенный архив в отдельный каталог. Проверяет выход за пределы каталога, абсолютные пути и ссылки, ограничивает объём распаковки. Ошибка пароля не удаляет полученный архив; существующие пользовательские файлы не перезаписываются молча.

## 7. Транспортный протокол

### Текущий AQR1

Бинарный заголовок `>4sB8sHHHI`, big-endian, **23 байта**:

| Поле | Байты | Назначение |
| --- | ---: | --- |
| magic | 4 | `AQR1` |
| type | 1 | 0 — метаданные, 1 — данные |
| file_id | 8 | Первые 8 байт SHA-256 передаваемого содержимого |
| index | 2 | Данные: 1…total; метаданные: 0 |
| total | 2 | Количество чанков данных |
| payload_len | 2 | Размер полезной нагрузки |
| crc32 | 4 | CRC32 только полезной нагрузки |

За заголовком следует бинарная полезная нагрузка. JSON метаданных содержит `filename`, `size`, `sha256`, `protocol`.

Предел: 65 535 чанков, около **175 МиБ** при чанке 2800 байт. Практический предел ниже из-за времени передачи и хранения всех кадров в памяти.

### Развитие протокола

- Несколько QR на экране можно внедрить поверх AQR1: каждый QR содержит самостоятельный пакет с собственным индексом.
- Изменение значения полей или структуры заголовка требует новой версии, например AQR2. Нельзя молча изменить AQR1.
- Для AQR2 предусмотреть случайный идентификатор передачи, 32-битные индексы и количество чанков, объявление формата контейнера и проверку заголовка вместе с payload.
- Параметры передачи фиксируются после принятия согласованных метаданных. Конфликтующие `total`, метаданные и содержимое одного индекса не должны незаметно заменять принятые значения.
- Пакеты проверяются по типу, длине, индексу, версии и лимитам ресурсов до сохранения. Приём до метаданных допускается с ограниченным буфером.
- Периодические метаданные обязательны для позднего подключения; их частота настраивается и входит в расчёт накладных расходов.
- Приёмник сохраняет подтверждённые чанки и описание сессии на диск, возобновляет сборку после перезапуска и показывает недостающие диапазоны.
- Базовая защита от пропусков — повторение цикла. Дополнительные восстанавливающие пакеты (FEC) рассматриваются после измерений: они могут сократить повторные циклы, но увеличивают код отправителя.

Эти правила описывают собственный пакетный транспорт QR/RGB-QR. Для cimbar сначала использовать его штатный протокол сборки, если он подходит: не накладывать AQR1 и второй слой FEC без необходимости. Общий для форматов результат — точные байты зашифрованного архива с проверкой целостности; конкретные пакеты, метаданные и состояние восстановления относятся к выбранному транспорту.

## 8. QR и размещение на Full HD

Этот раздел относится к QR-профилю. Ограничения версии 40 и тихой зоны QR не распространяются на cimbar или другой формат. В notebook доступная область меньше физического экрана, пока плеер не переведён в полноэкранный режим.

QR версии 40 содержит 177×177 модулей. С тихой зоной по 4 модуля с каждой стороны получается квадрат **185×185 модулей**. Это следует из [таблицы версий DENSO WAVE](https://www.qrcode.com/en/about/version.html/) и [требований к полям QR](https://www.qrcode.com/en/howto/code.html).

Версия 40-L в байтовом режиме вмещает до 2953 байт. Для AQR1 теоретический предел payload — `2953 − 23 = 2930` байт. Начальный чанк 2800 байт оставляет запас; приближение к пределу проверяется генерацией и обратным декодированием. Вместимость зависит от режима и коррекции: для M/Q/H размер чанка нужно уменьшить по соответствующей таблице.

В таблице сетка обозначает столбцы × строки. Размер включает тихую зону, но не дополнительный промежуток и интерфейс.

| Сетка, V40 | Пикселей на модуль | Размер одного QR | Область сетки | Назначение |
| --- | ---: | ---: | ---: | --- |
| 1×1 | 5 | 925×925 | 925×925 | Надёжная начальная проверка |
| 2×1 | 5 | 925×925 | 1850×925 | Основной кандидат для Full HD |
| 2×2 | 2 | 370×370 | 740×740 | Слишком мелкие модули для базового профиля |
| 3×1 | 3 | 555×555 | 1665×555 | Эксперимент с большей плотностью |
| 4×2 | 2 | 370×370 | 1480×740 | Агрессивный эксперимент |
| 2×2, 4K | 5 | 925×925 | 1850×1850 | Дополнительный профиль при сохранении 4K |

На Full HD четыре V40 с модулем 3 px требуют 1110 px по высоте и не помещаются. Поэтому **два больших QR рядом** — первая конфигурация для оптимизации, а не четыре в сетке 2×2.

Правила показа:

- Целое число пикселей на модуль, без интерполяции и произвольного растяжения CSS.
- Полноэкранный показ; счётчики, подсказки и курсор не перекрывают QR и тихие зоны.
- Все ячейки кадра переключаются вместе, когда изображения готовы. В смешанном кадре каждый корректно прочитанный пакет всё равно принимается независимо.
- При уменьшении области показа пересчитывать профиль, а не сжимать прежнюю сетку. Падение разрешения только на стороне VDI-клиента отправитель может не заметить: нужен ручной выбор профиля и диагностика приёмника.
- Максимальная версия — кандидат, а не гарантия максимальной скорости. Сравнить V40 с менее плотными версиями и коррекцию L с M.

## 9. Цветной режим

Цветность — экспериментальное расширение транспорта с отдельным включением. Просто заменить чёрный цвет QR другим цветом недостаточно для увеличения вместимости.

Предлагаемый вариант **RGB-3**:

1. Сформировать три независимые бинарные QR-матрицы одинаковой версии и геометрии.
2. Поместить их значения в R, G и B одного изображения: каждый модуль принимает один из восьми цветов.
3. На хосте разделить снимок на каналы, откалибровать пороги и декодировать каждую полученную монохромную матрицу.
4. Каждый слой несёт отдельный пакет обычного протокола; успешное чтение одного слоя не зависит от двух остальных.

Восемь различимых цветов кодируют `log2(8) = 3` бита на модуль вместо одного: идеальная ёмкость на той же площади увеличивается втрое. Две QR-позиции с тремя слоями дают до шестикратной ёмкости кадра относительно одного монохромного QR той же версии при одинаковой коррекции и частоте. Поэтому поддержка восьми цветов — существенное направление увеличения скорости, включённое в план реализации. Достижение такого множителя на реальном канале требует проверки потерь и скорости декодирования.

Риски для проверки: VDI может изменять цвет и применять сжатие с уменьшением разрешения цветовых компонент, масштабирование может смешивать соседние модули, а три декодирования увеличивают нагрузку хоста. При необходимости добавить вне тихих зон калибровочные цветовые поля и промежуточный режим с двумя слоями.

Управляющий/калибровочный кадр должен быть монохромным и периодически повторяться. Приёмник должен явно знать профиль цвета: обычный декодер не обязан читать наложенный RGB-QR. Гарантированный резервный вариант — переключение отправителя на монохромный режим; обратного автоматического управления через канал нет.

Цветной профиль становится рекомендуемым только если он сокращает время полного восстановления относительно лучшего монохромного профиля на том же VDI.

### Альтернативный формат: cimbar

**Стандарт QR не является требованием проекта.** Cimbar включается в раннее сравнение кандидатов, до окончательного выбора цветного транспорта.

В [sz3/cimbar](https://github.com/sz3/cimbar) данные кодируются формой и цветом плитки: 16 форм дают 4 бита, цвет добавляет ещё 2–3. Python-реализация обозначена автором как исследовательский, медленный прототип. Для старого восьмицветного режима 8C указано 8750 байт после стандартной коррекции на изображение. Это характеристика конкретного режима, а не гарантированная вместимость любого cimbar-кадра.

В [sz3/libcimbar](https://github.com/sz3/libcimbar) есть оптимизированная C++-реализация, браузерный WASM-кодировщик и автономный `cimbar_js.html`. Штатный файловый транспорт использует fountain codes (`wirehair`) и zstd, восстанавливая файл из достаточного количества различных блоков. README указывает предел 33 MB после сжатия; применимость к выбранной версии нужно проверить. Эти свойства делают реализацию кандидатом для браузерного отправителя.

**Семь бит на плитку cimbar нельзя напрямую сравнивать с одним битом на модуль QR:** площадь плиток, служебные области и коррекция различаются. Сравнивать полезные байты на кадр одинакового физического размера и время полного восстановления.

| Вариант | Интеграция в JupyterHub | Что необходимо проверить |
| --- | --- | --- |
| Моно QR | Python-библиотеки → компактный HTML-плеер | Базовая скорость и совместимость вывода |
| RGB-QR, 8 цветов | Три матрицы → один цветной кадр | Сохранность каналов и скорость трёх декодирований |
| Python cimbar | Кодирование в Python → кадры в плеер | Поставка через зеркало или перенос исходников, Python 3.10, скорость подготовки |
| libcimbar WASM | Зашифрованный архив из Python-окружения → локальный браузерный кодировщик | Размер/доставка бандла, разрешения браузера, интерфейс передачи байтов в браузер |

План проверки применимости cimbar:

1. Проверить наличие пригодного пакета и зависимостей в зеркале. Не считать, что `pip install cimbar` автоматически устанавливает именно указанный проект или libcimbar.
2. Для WASM выяснить способ однократной доставки ресурсов в окружение JupyterHub. Во время передачи не обращаться к публичному cimbar.org. Стандартный выбор файла в браузере сам по себе не даёт доступа к файлам удалённого Python-окружения: нужен явный путь передачи подготовленного архива в кодировщик.
3. На хосте адаптировать декодер к снимкам экрана. ZXing не заменяет декодер cimbar; отдельный процесс/библиотека допустимы. Проверить сборку и доступность бинарников для ОС хоста.
4. Передать уже зашифрованный архив, проверить побайтное восстановление и пароль. Штатное сжатие транспорта не заменяет шифрование; повторное сжатие зашифрованных байтов обычно не даёт выигрыша.
5. Проверить предел размера, накладные расходы и возобновление. Для fountain codes нужно сохранять подходящее состояние декодера либо принятые блоки; перечень недостающих индексов AQR1 к ним напрямую не применим.
6. Если потребуется деление архива на несколько самостоятельных передач, отдельно определить манифест частей и итоговую проверку. Не обещать поддержку произвольного размера за пределами выбранной реализации.

Предпочтение отдаётся готовому кодеку при достижимой компактной поставке. Собственный формат плиток имеет смысл только если существующие варианты не удовлетворят измеренным требованиям.

## 10. Пропускная способность

Приближённая модель:

Для QR/RGB-QR с нумерованными чанками:

```text
R = B × Q × C × F × D × U
```

- `B` — полезные байты одного пакета без заголовка.
- `Q` — число QR-позиций в кадре.
- `C` — число независимых цветовых слоёв: 1 для монохромного режима.
- `F` — фактическая частота смены кадров.
- `D` — доля позиций со служебно полезными данными архива, исключая метаданные.
- `U` — доля этих позиций, давших новый проверенный чанк; учитывает потери и повторы.
- `R` — скорость накопления уникальных байтов архива, байт/с.

Расчётные примеры при `B=2800`, `D=8/9`, `U=1`:

| Режим | Частота показа | Скорость архива |
| --- | ---: | ---: |
| 1 QR, моно | 1,67 кадра/с, около текущих 600 мс | 4,05 КиБ/с |
| 2 QR, моно | 5 кадров/с | 24,31 КиБ/с |
| 2 QR, моно | 10 кадров/с | 48,61 КиБ/с |
| 2 QR, RGB-3 | 10 кадров/с | 145,83 КиБ/с |

Это арифметические ориентиры без потерь, не результаты тестов. `D=8/9` приближённо соответствует текущей вставке метаданных; в новых профилях расписание может отличаться. При `U=0,7` скорость составит 70% указанной. Ожидание последних пропущенных чанков может заметно увеличить время завершения.

Для архива 10 МиБ при 24,31 КиБ/с идеальное время передачи — около 7 минут; отдельно учитываются упаковка, подготовка QR и распаковка. Текущий таймаут приёмника 300 секунд для этого недостаточен.

Замерять отдельно скорость архива и скорость исходных данных: коэффициент сжатия может значительно менять итоговый результат. Наращивать FPS следует только пока растёт скорость новых чанков.

Для cimbar измерять размер восстановленного зашифрованного архива, делённый на время передачи до успешного восстановления. Полезную ёмкость кадра брать из выбранного режима кодека с учётом его FEC и файлового протокола. Не переносить множитель RGB-3 на уже цветной cimbar. Для всех форматов отдельно учитывать доставку подготовленных данных из Python-окружения в браузер и запуск плеера.

## 11. Развитие приёмника

- Область захвата (ROI) вместо обязательного анализа всего монитора.
- Чтение нескольких QR через `read_barcodes` либо отдельное декодирование известных ячеек. API нескольких результатов описан в [Python-обёртке ZXing-C++](https://github.com/zxing-cpp/zxing-cpp/blob/master/wrappers/python/README.md).
- Ограниченная очередь захвата; не накапливать устаревшие снимки при отставании декодера.
- Частота захвата с учётом времени обработки; статистика фактического FPS и времени декодирования.
- Дедупликация пакетов, сохранение на диск и восстановление состояния сессии.
- Прогресс: получено/всего, новые байты/с, дубликаты, ошибки CRC, пропуски, время без новых данных.
- Таймаут отсутствия прогресса отдельно от общего лимита времени. По таймауту сохранённые чанки остаются доступны.
- Отдельные счётчики по QR-позиции и цветовому слою для обнаружения слабых участков изображения.
- Ручной ввод диапазонов недостающих чанков в отправителе можно добавить позднее; он не должен быть условием успешной передачи.
- Разделить захват экрана и декодер транспорта: QR/RGB-QR возвращает пакеты, cimbar — результат своего процесса восстановления. Общими остаются проверка контейнера, пароль, распаковка и итоговые метрики.

## 13. Проверка и критерии приёмки

### Корректность

- Пустой файл, небольшой текст, случайные бинарные данные, уже сжатый файл, каталог с Unicode-именами и вложенными папками.
- Граничные размеры: ровно один чанк, на байт меньше/больше, неполный последний кадр с несколькими QR.
- Подключение в середине цикла; пропуск метаданных; дубликаты, перестановка и потеря пакетов; завершение после повторного цикла.
- Повреждённые заголовки/payload, чужая сессия, конфликтующий пакет с тем же индексом, некорректные метаданные.
- Перезапуск приёмника с продолжением сбора; неверный пароль; занятое имя результата; небезопасные пути в архиве.
- После распаковки совпадают имена, размеры и SHA-256 исходных файлов; ошибочный результат не помечается успешным.

### Экран и производительность

- Запуск из реального JupyterHub под Python 3.10 с установкой из внутреннего PyPI; отдельная проверка совместимости с 3.12.
- Проверить выбранный способ запуска и открытия плеера, разрешения JavaScript/WASM, запуск/остановку и перезагрузку страницы. Если поддерживается notebook, отдельно проверить повторное выполнение ячейки и встроенный вывод.
- Проверить фактическую область показа без полноэкранного режима, время доставки данных в браузер и отсутствие пароля в сохраняемых артефактах. Лимиты вывода и сохранённый notebook проверять для интеграции через ячейки.

- Проверить Full HD и 4K, уменьшение разрешения во время передачи, масштабы ОС/VDI 100%, 125%, 150% там, где они доступны.
- Сначала моно: 1 и 2 QR, V40-L и V40-M, затем менее плотные версии. Начальные частоты: 2, 5, 8, 10 кадров/с; это точки эксперимента, не гарантия поддержки.
- Затем сравнить плотные сетки, RGB и cimbar на одинаковом зашифрованном входе, одинаковой площади показа и одинаковых настройках канала. Для cimbar добавить случаи потерь блоков и достижения порога восстановления.
- Синтетические изображения использовать для проверки кодека, реальную VDI-сессию — для вывода о пропускной способности.
- Для финальных кандидатов выполнить минимум три полные передачи одного и того же набора; записать медиану и худшее время, процент успешных завершений, загрузку CPU и пиковую память.
- Учитывать всё время от запуска упаковки до готового результата, отдельно выделяя передачу.

Базовый релиз принимается при успешном прохождении проверок корректности, запуске в JupyterHub на Python 3.10, повторяемом полном восстановлении на Full HD, наличии пароля и возобновления, а также измеренном размере ручного переноса и описанной установке из зеркала. Выбранный основной формат должен пройти все эти проверки; остальные могут поставляться экспериментальными с указанием проверенных условий.
