# И00: запуск диагностики и контрольной передачи

[План итерации](../iterations/00-environment-baseline.md) · [Результаты локальной проверки](../reports/environment.md)

Набор готов к запуску. **Автономная диагностическая страница проверена в реальном JupyterHub; fullscreen во встроенном просмотрщике не открывается, но работает после отдельного открытия страницы. Контрольная передача через VDI ещё требует подтверждения результата.** Отправитель запускается из доступного терминала JupyterHub; notebook не нужен. Приёмник — на Windows-хосте пользователя.

Все команды ниже выполняются из корня скачанного репозитория. Для повторного прогона выбирайте новый выходной каталог/имя отчёта: утилиты намеренно не перезаписывают прошлые результаты. Файлы `artifacts/` и `.venv-i00/` исключены из Git.

## 1. Первая проверка на JupyterHub без установки пакетов

В терминале JupyterHub:

```bash
python3.10 tools/i00.py probe --role jupyterhub --output artifacts/i00/jupyter-before.json
python3.10 tools/i00.py fixtures --output artifacts/i00/fixtures
python3.10 tools/i00.py browser --output artifacts/i00/browser
```

Если интерпретатор называется `python` или `python3`, сначала проверьте `--version` и используйте фактическое имя. Если 3.10 недоступен, запуск под 3.12 допустим для диагностики; это не подтверждает проверку основной версии.

`probe` использует стандартную библиотеку, определяет ОС/интерпретатор, версии и импорты установленных пакетов, права записи, диск и доступные лимиты процесса. При наличии `psutil` также измеряет RAM; иначе это поле имеет статус `not_checked`. На Linux отдельно читает доступные memory limits cgroup. Это помогает отличить RAM сервера от лимита пользовательского контейнера.

Отчёт не обращается в PyPI, не устанавливает пакеты, не выгружает переменные окружения/конфигурацию pip и не записывает токены JupyterHub. Пути интерпретатора и проверяемого файла остаются в локальном JSON; перед передачей отчёта можно скрыть личные части путей. `installed_wheel_tags` описывает установленный пакет, **не доступность wheel во внутреннем зеркале**.

Содержимое тестового файла можно проверить отдельно:

```bash
python3.10 tools/i00.py probe --role jupyterhub --source artifacts/i00/fixtures/binary.bin --output artifacts/i00/jupyter-source.json
```

Ожидаемые исходные данные детерминированы: `binary.bin` — 64 КиБ, `tree/` — случайный файл 64 КиБ, Unicode-текст, пустой файл и пустой каталог. Для другого объёма используйте `fixtures --size-kib 128` или `256` в новом каталоге. На обеих сторонах должен быть один размер и одна версия генератора.

## 2. Установка отправителя из существующего зеркала

```bash
python3.10 -m venv .venv-i00
source .venv-i00/bin/activate
python -m pip install -r requirements/i00-sender.txt
python tools/i00.py probe --role jupyterhub --source artifacts/i00/fixtures/binary.bin --output artifacts/i00/jupyter-after.json
```

Команда pip использует уже настроенный источник. Не подставляйте учётные данные зеркала в команды или отчёт. Если в JupyterHub предусмотрено другое пользовательское окружение вместо `venv`, используйте его и сохраните фактический путь Python из отчёта.

Диапазоны в requirements — кандидаты с учётом Python 3.10. На этом этапе важно записать фактически установленные версии и наличие нужных wheels. Успешная установка на Windows из публичного источника не доказывает доступность Linux wheels во внутреннем PyPI.

Для статистики памяти подготовки можно отдельно установить `psutil`. Кандидаты следующих итераций проверяются отдельно: `py7zr`, `segno`, `numpy`, `raptorq`. Устанавливайте их по одному, чтобы ошибка одного не скрывала результат остальных; затем повторите `probe` в новый JSON. Для проверки именно готовых wheels используйте `python -m pip install --only-binary=:all: ИМЯ_ПАКЕТА`. Неуспех такой команды означает отсутствие подходящей бинарной поставки в данном источнике, а не доказанную невозможность сборки из исходников.

## 3. Открытие диагностической страницы в JupyterHub

Для JupyterLab сначала используйте **`artifacts/i00/browser/standalone.html`**. Команда `browser` создаёт этот автономный файл со встроенным приложением и кодом worker. Соседние JS/JSON для показа не нужны; worker из Blob и WASM проверяются отдельно и могут быть запрещены политикой просмотрщика.

Для проверки именно внешних ресурсов остаётся комплект `index.html`, `diagnostic.js`, `worker.js`, `probe.json`; эти четыре файла должны оставаться рядом. В автономном варианте `external_script` и `relative_json_fetch` имеют статус `not_tested`, а `worker_source` — `blob`. Это не доказывает работоспособность внешних ресурсов.

Если встроенный JS выполнен, а основной — нет, как на предоставленном скриншоте JupyterLab, откройте `standalone.html`. Возможны ошибка загрузки, блокировка или ошибка выполнения внешнего скрипта; один скриншот не различает причины. В просмотрщике надпись **Distrust HTML** уже означает доверенное состояние — повторно переключать её не нужно. Поведение кнопки описано в [исходнике HTMLViewer JupyterLab](https://raw.githubusercontent.com/jupyterlab/jupyterlab/main/packages/htmlviewer/src/widget.tsx).

После обновления репозитория создайте новый каталог, сохранив прежние результаты:

```bash
python tools/i00.py browser --output artifacts/i00/browser-v2
```

Откройте `artifacts/i00/browser-v2/standalone.html`. Следующие пункты также применимы к `index.html` при отдельной проверке внешних ресурсов.

1. В файловом интерфейсе JupyterHub откройте `standalone.html` как HTML/отдельную страницу доступным в вашей конфигурации способом. Просмотр исходника в редакторе не выполняет JavaScript.
2. Если доступен файловый маршрут Jupyter Server, попробуйте страницу по нему. Типовая форма — `<пользовательский префикс>/files/<путь относительно корня Jupyter>/index.html`; фактический префикс, корень и разрешения зависят от конфигурации. Не копируйте токены из полного URL в отчёты.
3. Проверьте два отдельных индикатора: выполнение встроенного JS и выполнение основного внешнего JS. При запрете активного HTML остаётся исходное сообщение, а отчёт может не появиться.
4. Запустите счётчик, затем паузу, один шаг, изменение частоты/клетки и fullscreen. В fullscreen доступны Space для паузы и Esc для выхода; управляющие кнопки остаются вне тестовой области.
5. Измените размер окна, перезагрузите страницу. На 5 Гц переключите вкладку на несколько секунд и вернитесь: событие visibility попадёт в отчёт, но браузер не узнает, сколько кадров дошло через VDI.
6. Выберите способ открытия в поле отчёта и сохраните JSON либо скопируйте его из текстового поля. Сохранение браузером происходит на устройстве браузера/VDI и само по себе не передаёт JSON на хост.

Если серверный просмотр блокирует скрипты, зафиксируйте отказ и доступные варианты. Дополнительный путь — сохранение полного комплекта на **сам VDI** и открытие локального HTML, если этот путь разрешён и доступен. Для `file://` отдельные JSON/worker-проверки могут не пройти; это отдельный результат, а не автоматически неисправный mono-плеер. Файловая система браузера и JupyterHub может различаться.

Защиты JupyterHub/CSP не отключаются. Установка нового веб-сервера не является условием запуска. Сведения о доверии и безопасности сервера: [Jupyter Server security](https://jupyter-server.readthedocs.io/en/latest/operators/security.html).

### Отступ под панель VDI

Перед входом в полный экран выберите «Отступ сверху в полном экране»: по умолчанию 48 CSS px, доступны 0/24/48/64/96/128. Если панель подключения всё ещё перекрывает рисунок, выйдите через Esc, увеличьте отступ и снова откройте полный экран. Рисунок занимает оставшуюся высоту без обрезания; в оконном режиме отступ не применяется. JSON содержит `fullscreen_top_css_px`, `applied_fullscreen_top_css_px` и `css_canvas_origin`. CSS-пиксели могут отличаться от пикселей захвата хоста.

### Если fullscreen не открывается

Во встроенном просмотрщике JupyterHub fullscreen может ограничиваться разрешениями родительского iframe или Permissions Policy. Это отдельное разрешение от выполнения JavaScript; работа Canvas/worker/WASM не гарантирует fullscreen. В отчёте после нажатия кнопки поле `features.fullscreen` содержит результат запроса. В текущем реальном тесте пользователь подтвердил, что режим не открывается; точный код ошибки пока не получен.

Для контрольного приёма можно продолжать в окне, оставив код целиком видимым. Для увеличения доступной области попробуйте открыть `standalone.html` отдельной вкладкой браузера через доступный файловый маршрут Jupyter Server (см. выше), затем кнопку «Полный экран». Вкладка внутри JupyterLab всё ещё является встроенным просмотрщиком. Если маршрут скачивает HTML, файл можно открыть браузером на самом VDI при доступности такого способа.

F11 в браузере VDI — ещё один вариант увеличения окна; он может перехватываться клиентом VDI. F11 не подтверждает работу Fullscreen API и не убирает интерфейс самого JupyterLab. Политики сервера менять для контрольного приёма не требуется. [Требования Fullscreen API](https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen#security_considerations).

Для измерения частоты сначала на паузе выберите частоту и клетку, затем нажмите «Сброс» и «Старт», через 20–30 секунд — «Пауза». Каждый профиль измеряйте отдельно: счётчик усредняет весь прогон и не сбрасывается при смене настроек. Это частота отрисовки браузера, а доставку кадров проверяет приёмник на хосте.

### Что означают проверки

| Поле | Что доказано при `ok` |
| --- | --- |
| `inline_script` / `external_script` | Этот вид JS действительно выполнился |
| `relative_json_fetch` | Браузер получил ожидаемый локальный JSON из соседнего файла |
| `worker` | Отдельный локальный worker запустился и ответил |
| `wasm` | Разрешена компиляция минимального WASM-модуля; libcimbar этим не проверяется |
| `fullscreen` | Запрос fullscreen прошёл после нажатия; до нажатия `not_tested` |
| `actual_updates_per_second` | Частота вызовов отрисовки браузера за активное время, включая фоновые задержки |

Крупные восемь цветовых полей — начальная визуальная диагностика. Они **не заменяют [Э01](../experiments/01-vdi-color-channel.md)**, который измерит ошибки мелкой динамической сетки на хосте.

## 4. Подготовка контрольных HTML на JupyterHub

В окружении с установленными sender-зависимостями:

```bash
python tools/i00.py prepare --fixtures artifacts/i00/fixtures --output artifacts/i00/prepared
```

Утилита запускает существующий `code.py` без изменения протокола. Получаются `binary.html`, `tree.html`, два журнала и `prepare.json` с размером HTML, числом кадров, временем и памятью, если доступен `psutil`. Настройки фиксированы: AQR1, V40-L, чанк 2800, 600 мс, PNG 1110×1110 и исходное CSS `90vmin`.

Используются только синтетические данные: текущий прототип не шифрует передачу. Для каталога создаётся tar.xz; для файла передаются исходные байты. `prepare` возвращает ненулевой код при провале хотя бы одного случая и сохраняет оба результата.

## 5. Приём на Windows-хосте

Подготовка в PowerShell:

```powershell
py -3.12 -m venv .venv-i00
.\.venv-i00\Scripts\python.exe -m pip install -r requirements/i00-host.txt
.\.venv-i00\Scripts\python.exe tools/i00.py fixtures --output artifacts/i00/fixtures
.\.venv-i00\Scripts\python.exe tools/i00.py probe --role host --capture --monitor 2 --output artifacts/i00/host.json
```

На текущем хосте проверен Python 3.12.10. Если `.venv-i00` и fixtures уже созданы в этой рабочей копии, повторно их создавать не нужно. `--capture` захватывает три снимка только в память и сохраняет геометрию/время, без изображений рабочего стола.

По текущему замеру монитор 1 — 3840×2160, монитор 2 — 1920×1080; номера могут поменяться после переподключения. Монитор 0 означает объединённый рабочий стол. Выберите монитор, на котором виден VDI, и сначала используйте фактический Full HD. Геометрия из probe не раскрывает масштаб VDI — его нужно записать отдельно.

Запустите приём, затем откройте соответствующий `binary.html` в браузере VDI:

```powershell
.\.venv-i00\Scripts\python.exe tools/i00.py receive --fixtures artifacts/i00/fixtures --case binary --level real_vdi --monitor 2 --output artifacts/i00/vdi-binary-1
```

Повторите для `vdi-binary-2` и `vdi-binary-3`. Затем для `tree.html`:

```powershell
.\.venv-i00\Scripts\python.exe tools/i00.py receive --fixtures artifacts/i00/fixtures --case tree --level real_vdi --monitor 2 --output artifacts/i00/vdi-tree-1
```

Повторите для `vdi-tree-2` и `vdi-tree-3`. Обе стороны генерируют один и тот же тестовый набор независимо; передавать исходные fixtures из VDI на хост не требуется.

Обёртка запускает исходный `qr.py`, сохраняет его stdout/stderr в `receive.log` и независимо проверяет результат по манифесту. **Код возврата 0 у старого `qr.py` бывает также при таймауте** — поэтому успех требует наличия результата и совпадения данных, а не только exit code. `receive.json` сохраняется и для неудачной попытки.

Для каталога проверяются имена, размеры, SHA-256, пустые файлы/каталоги внутри полученного tar.xz. Автоматической распаковки рабочего архива здесь нет: тестовый архив читается без записи его путей на диск. Время в отчёте начинается с запуска приёмника и включает ожидание показа; это не очищенный от ожидания `goodput` будущего стенда И08.

Исходный приёмник всё ещё захватывает весь монитор и хранит чанки в RAM. ROI, возобновление, AQR2 и пароль появятся в следующих итерациях.

## 6. Локальные проверки для разработки

PNG round-trip без браузера и VDI:

```powershell
.\.venv-i00\Scripts\python.exe tools/i00.py roundtrip --fixtures artifacts/i00/fixtures --prepared artifacts/i00/prepared --output artifacts/i00/png-roundtrip --runs 3
.\.venv-i00\Scripts\python.exe -m unittest discover -s tests -v
```

Дополнительно, с `requirements/i00-dev.txt` и установленным Chrome/Edge:

```powershell
.\.venv-i00\Scripts\python.exe tools/check_i00_browser.py --channel chrome --prepared artifacts/i00/prepared --fixtures artifacts/i00/fixtures --output artifacts/i00/browser-check
```

Этот тест поднимает временный сервер **только на 127.0.0.1** для файлов диагностики и запускает headless-браузер. Он проверяет JS/worker/WASM, управление, resize, отчёт и декодирует снимки синтетических QR в viewport 1920×1080. Кадры переключаются пошагово; результат не является измерением физического захвата или скорости 600 мс/кадр. Для Edge используйте `--channel msedge`.

## 7. Что нужно для закрытия И00

- Отчёты JupyterHub до/после установки: ОС, Python 3.10, зависимости, исходный путь и лимиты.
- Реальный рабочий маршрут активного HTML; результат JS/worker/WASM/fullscreen и настройки масштаба.
- Три приёма каждого тестового случая через экран VDI с сохранёнными удачами/неудачами.
- Время подготовки на JupyterHub, размер HTML, доступная память и условия каждого прогона.

При невозможности вынести JSON из JupyterHub достаточно сообщить ключевые значения текстом для первичной диагностики. Полный отчёт можно позже передать проверенным визуальным каналом; ожидание его не мешает начать тестирование страницы и baseline.
