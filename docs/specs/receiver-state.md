# И04: хранилище и приёмник

## Транзакционная сессия

`storage.DurableSession` используется новым `capture`. Старые `receive/resume`
для файлов AQS1 сохраняют поведение И01; форматы нельзя смешивать.

- `packets.sqlite3`: SQLite user_version=1, таблица
  `packets(seq INTEGER PRIMARY KEY, kind, idx, raw BLOB, UNIQUE(kind,idx))`.
- Первая запись — metadata; затем только принятые уникальные DATA текущего ID.
- `chunks/*.bin` — восстанавливаемый кэш; `object.part` — временная сборка;
  `object.bin` — проверенный зашифрованный объект.
- `status.json` — снимок состояния, `capture.json` — последний запуск,
  `extraction.json` — отдельный результат распаковки И02.

Используется rollback journal SQLite, `synchronous=FULL`, кэш SQLite 2 МиБ.
Отдельного spool нет: байты пакета и его индекс фиксируются одной транзакцией.
Порядок принятия DATA: записать кэш → INSERT и COMMIT → добавить индекс в память
и увеличить `received_chunks`. `committed_chunks` увеличивается только после
успешного COMMIT. Дубликаты не вызывают INSERT; очереди принятых, но ещё не
зафиксированных чанков нет. Надёжность fsync зависит от файловой системы/диска.

Сбой до COMMIT оставляет максимум лишний файл кэша; он не считается принятым.
При открытии после аварии SQLite откатывает незавершённую транзакцию. Проверяются
версия, quick_check, лимиты строк/байтов, CRC и смысл каждого пакета, metadata,
ID/число чанков/длины. Индекс и кэш восстанавливаются последовательным чтением
подтверждённых записей. Повреждённая подтверждённая запись — явная ошибка, а не
повод без уведомления забыть часть данных. Повреждённый кэш можно восстановить.

Сборка читает чанки по одному, записывает/синхронизирует `object.part`, проверяет
размер и SHA-256, затем атомарно заменяет `object.bin`. После аварии между COMMIT
последнего чанка и публикацией сборка повторяется. Уже готовый объект при resume
также восстанавливается и перепроверяется, после чего приём кадров не нужен.
Исходные пользовательские файлы публикует только модуль контейнера И02.

`.writer.lock` имеет постоянный inode и блокировку ОС: byte lock Windows,
flock Linux. Второй писатель получает `session_locked`. После аварии ОС освобождает
блокировку; проверять PID и удалять «старый» lock-файл не нужно. Проверено локально
на Windows; Linux-ветка ещё не проверена исполнением.

Перед metadata требуется запас `3*object_size + total*8192 + 16 МиБ`; перед
каждым COMMIT — минимум 64 КиБ + 16 МиБ. Это консервативная проверка свободного
места, не резервирование: параллельный расход диска всё равно может вызвать отказ.
При resume проверяется место для восстановления кэша/объекта. Входная SQLite
ограничена размером, числом записей и длиной BLOB до выдачи пакетов в ядро.
Лимиты транспорта остаются 64 МиБ / 65536 чанков. Состояние не очищается автоматически.

## Захват, декодирование, транспорт

`LatestFrames` создаёт mss в потоке захвата. В очередь помещаются RGB-снимки PIL,
не более двух ожидающих; ещё один может декодироваться и один создаваться.
При заполнении удаляется самый старый ожидающий снимок и растёт `dropped_old`.
Новый захват планируется по monotonic deadline с учётом времени предыдущего;
поток декодирования не добавляет sleep. Для измерений сохранён синхронный путь.

mss 10.2.0 и zxing-cpp 3.1.1 закреплены в зависимостях. ROI задаётся относительно
монитора в физических пикселях; глобальные координаты могут быть отрицательными.
Топология mss обновляется раз в секунду через его версионно-зависимый кэш.
Если ROI после resize не помещается, применяется весь монитор с диагностическим
флагом. Исчезновение монитора требует выбора нового и resume.

`MultiDecoder` читает `read_barcodes(..., formats=QRCode)` и возвращает bytes,
позицию и время. После успешного поиска запоминает до двух прямоугольников
с запасом; повторно декодирует их отдельно. Неудача любой позиции, смена размера
или истечение секунды вызывает полный поиск области. Это позволяет обнаружить
перемещение и новый второй QR. Дефект одной позиции не блокирует другую.
Fingerprint-пропуск кадров не включён: он не нужен для корректности и требует
отдельного измерения перед работой с будущими цветовыми слоями.

Декодер и запись в SQLite выполняются в основном потоке. Два decode-потока в
локальном измерении выполняют работу параллельно, но текущему профилю хватает
одного потребителя. Процессы не используются: не нужны дополнительные копии
Full HD/4K кадров между процессами. Сравнение режимов приведено в отчёте.

Метрики позиций — пространственные результаты слева направо при полном поиске,
а не постоянный ID слота в протоколе. После перемещения/скрытия позиции нумерация
может измениться. Время decode включает поиск; capture относится ко всему снимку.
Прогресс/скорость относятся к новым уникальным байтам текущего запуска; общее
количество принятых/зафиксированных чанков включает восстановленные.
RSS — выборка процесса приёмника, не суммарная память браузера и VDI.
Историческое поле `capture_fps` верхнего уровня и консольный `processed/s`
обозначают обработанные снимки/с. В `pipeline.capture_fps` учитываются все
захваты, включая отброшенные; `pipeline.processed_fps` — обработанные.

## Два слота плеера

QRM1/AQR2 и пакетизация И03 не меняются. В config добавлены `slots=1|2` и
`update_mode=sync|staggered`. В расписании периодические metadata занимают обычные
позиции; нечётный набор для двух слотов дополняется повтором metadata. Никаких
пустых QR или несуществующих индексов нет.

Sync обновляет все слоты раз в интервал; staggered обновляет очередной слот
раз в `interval/slots`. Полный цикл занимает `padded_symbols*interval/slots`.
Задержки браузера не наверстываются пачкой; фактическая частота каждого слота
записывается отдельно. Смена расположения/режима может повторить текущие кадры,
сохраняет ID и не требует новой упаковки. Оба QR имеют собственную тихую зону;
между ними дополнительно 8 backing pixels. Масштаб всегда целочисленный.
