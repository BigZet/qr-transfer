# И00: состояние среды и локальные результаты

Дата проверки: **15 сентября 2026 года**. [Инструкция запуска](../usage/iteration-00.md) · [План И00](../iterations/00-environment-baseline.md) · [Исходные числовые результаты](../../benchmarks/baseline/local-2026-09-15.json)

## Статус итерации

**Инструменты реализованы, локальные проверки пройдены; автономная диагностическая страница работает в реальном JupyterHub. И00 полностью не закрыта:** результаты установки из внутреннего зеркала и контрольной передачи через VDI ещё требуют подтверждения. Fullscreen во встроенном просмотрщике не открывается; пользователь подтвердил успешный полноэкранный запуск после отдельного открытия страницы.

Подтверждено пользователем: приёмник находится на текущем Windows-хосте, терминал JupyterHub доступен. На предоставленном скриншоте отчёта подтверждены **Python 3.10.12, Linux x86_64, glibc 2.34**, интерпретатор `/usr/local/bin/python` и `preferred_python_310=true`. Дистрибутив Linux не установлен; строка версии GCC с Red Hat и версия ядра не подтверждают дистрибутив пользовательского контейнера. Полный JSON и раскрытые результаты зависимостей пока не получены.

### Уточнение по запуску HTML

На первом скриншоте JupyterLab встроенный JS выполнен, основной внешний JS не запущен, Canvas пуст. Это сужает причину до загрузки/выполнения внешнего приложения; не доказывает конкретный CSP-отказ. Подготовлен автономный `standalone.html`: приложение встроено в HTML, worker проверяется через Blob. Локально воспроизведена неисправность при недоступных соседних файлах и проверен рабочий автономный вариант в sandbox iframe с заблокированной сетью. Текущий набор unit tests: **14/14**.

Повторные скриншоты пользователя подтверждают работу автономного варианта в реальном JupyterHub: `route_declared=jupyter-embedded`, `url_protocol=blob:`, `embedded=true`; встроенное приложение, Canvas, Blob-worker и компиляция минимального WASM имеют статус `ok`. Внешние JS и JSON не проверялись. По последующему сообщению пользователя fullscreen не открывается; на предоставленном JSON он ещё `not_tested`, поэтому точный отказ API неизвестен. Возможная причина — разрешения родительского iframe/Permissions Policy; это гипотеза, а не установленная причина. Требования API описаны в [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen#security_considerations).

### Геометрия и частота по скриншотам реального JupyterHub

- CSS viewport: 1723×942; Canvas: около 1278,89×488,84 CSS px; backing buffer: 2302×880; DPR: около 1,8. `screen_css=1920×1080` не устанавливает физическое разрешение захвата хоста; оно не измерено.
- За 23,742 с работы записано 303 обновления, среднее 12,762 обновления/с. Во время этого прогона частота менялась на 60 Гц, затем клетка — на 3 px. Среднее объединяет разные настройки и не является отдельным замером профиля 60 Гц.
- Последние интервалы отрисовки преимущественно 62–94 мс. Диагностика заново рисует множество клеток на каждом кадре; её собственная нагрузка может влиять на частоту. Причина задержек не установлена.
- Эти данные описывают вызовы отрисовки браузера. Частота кадров, дошедших до приёмника через VDI, скорость передачи и сохранность цветов ещё не подтверждены.

Для сравнения профилей: выбрать частоту и клетку на паузе, выполнить «Сброс», затем отдельный прогон 20–30 с без смены настроек. Fullscreen не является обязательным условием контрольного приёма.

## Реализовано

- `tools/i00.py`: диагностика окружения и пакетов; воспроизводимые тестовые данные; подготовка HTML исходным отправителем; PNG round-trip; запуск исходного приёмника с независимой проверкой результата и отчётами.
- `diagnostics/browser/`: автономный комплект Canvas/HTML/JS с управлением, геометрией, счётчиком, проверками worker/WASM/локального JSON и экспортом отчёта.
- `tools/check_i00_browser.py`: headless-проверки страницы и декодирование снимков исходного HTML при Full HD.
- `requirements/i00-*.txt`: зависимости sender/host/dev и наблюдавшиеся локальные версии.
- `tests/test_i00.py`: проверки воспроизводимости, отказа от перезаписи, точности файла/каталога, обработки таймаута/отмены и результатов старого приёмника.

Файлы исходного прототипа `code.py` и `qr.py` не изменены. Ни парольный транспорт, ни AQR2, ни цветной декодер этим этапом не реализованы.

В browser round-trip кадры переключались пошагово. Размер QR после исходного CSS составил 972×972 px, то есть около 5,25 px на модуль с тихой зоной. Чтение в этом локальном случае прошло, но устойчивость дробного масштаба на VDI не доказана. Время 2,2–2,5 с на такой тест **не является скоростью передачи при интервале 600 мс**.

Крупные цветовые поля диагностической страницы проверяют её работу. Данных о сохранности восьмицветной динамической сетки на VDI пока нет; это отдельный Э01.

## Обнаруженные особенности

1. Старый `qr.py` возвращает exit code 0 также при таймауте. Обёртка признаёт успех только после независимой проверки ожидаемого файла/каталога; отказ сохраняет `receive.json` и лог.
2. При Ctrl+C приёмник и его дочерние процессы останавливаются, отчёт сохраняет `termination=interrupted`. Готового результата при этом не объявляется.
3. В sandbox агента были недоступны BitBlt и временные каталоги Python, в том числе созданные тестами. После разрешённого запуска вне sandbox проверки прошли. Эти ограничения не приписываются самому Windows-хосту или JupyterHub.

## Полноэкранный запуск и панель VDI

После отдельного открытия страницы пользователь подтвердил работу fullscreen и прислал снимок. Сверху рисунок перекрывает неснимаемая панель подключения VDI. Добавлен настраиваемый отступ только для fullscreen: 48 CSS px по умолчанию, варианты 0/24/48/64/96/128. Высота Canvas уменьшается на отступ; начало Canvas и заданный/применённый отступ записываются в JSON. Это браузерные координаты, а не замер пикселей хоста.

Локальная browser-проверка подтвердила геометрию при отступах 48/96/0 и снятие отступа после выхода. Достаточность 48 CSS px для конкретной панели нужно оценить на VDI; обновлённая версия там ещё не проверялась.
