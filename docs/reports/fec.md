# И05: сравнение repeat и межпакетного FEC

16 сентября 2026. **Реализован AQR2-LT v1; совместные проверки И04/И05 через VDI
выполняются после И05 по договорённости.** [Запуск](../usage/iteration-05.md) ·
[Спецификация](../specs/aqr2-lt.md).

## Выбор готовой библиотеки

| Кандидат | Проверка в текущем окружении | Решение |
| --- | --- | --- |
| RaptorQ 2.0.0 | Публичный Linux abi3 wheel найден; Windows-wheel отсутствует. Сборка Python bindings остановилась: `link.exe` не найден | Не интегрирован; нельзя обещать работоспособность без сборочной цепочки MSVC |
| Wirehair | `wirehair-fec` не найден в используемом реестре; нативная библиотека отдельно не установлена | API не проверен исполнением; штатный путь libcimbar остаётся для И07 |
| LT-code 0.3 | Установлен на Windows/Python 3.10.21 и 3.12.10, случайные бинарные данные восстановлены точно | Выбран для первого переносимого FEC-профиля |

Первичные источники: [поставка RaptorQ](https://pypi.org/project/raptorq/2.0.0/),
[Wirehair и Python bindings](https://github.com/catid/wirehair),
[LT-code 0.3](https://pypi.org/project/lt-code/0.3/),
[код LT encoder/decoder](https://github.com/anrosent/LT-code).
[Команды, ошибки и хеши поставки](../../benchmarks/fec/compatibility.json).

Для LT публичный sdist собран локально в `lt_code-0.3-py3-none-any.whl`.
Нативная компиляция не требуется. Проверены `encoder`, `BlockGraph`, `PRNG`;
механизм решения LT-графа взят из библиотеки. Адаптер ограничивает блоки, валидирует
пакеты, добавляет systematic-символы и сохраняет журнал. Другие реализации LT/RQ
не объявляются совместимыми. Linux и внутренний PyPI ещё не проверены исполнением.

## Методика и все попытки

[Полный JSON с 540 попытками и трассами](../../benchmarks/fec/local-2026-09-16.json).

Один зашифрованный архив **131 548 байт**; одинаковый бюджет **424 показанных
символа**, 0,3 с/символ (эквивалент 2 QR по 600 мс при идеальном расписании).
Это модель доставки пакетов, не wall-clock VDI. Издержки разных заголовков,
bootstrap, padding и repair входят в число показанных символов.

Три режима: repeat, LT systematic+3K repair, LT repair-only 3K. Для каждой из
9 конфигураций — 20 seed, одинаковые трассы между режимами:

- Независимые потери 0/5/10/20/40%.
- Серийные пропуски 0,5/2/5 с поверх 10% независимых потерь.
- Поздний старт без начальной metadata, дубликаты, CRC-повреждения и перестановка.

В этих 540 попытках все передачи завершились в бюджете. Для неполной передачи
стенд сохраняет `success=false` и `null` вместо времени успеха; такой результат
не исключается из доли успешных попыток. Отдельный тест малого repair-пула
подтверждает, что его повторение не превращает недостающую информацию в успех.

## Время завершения в модели

Медианы секунд по 20 трассам:

| Потери | Repeat | LT systematic | LT repair-only |
| --- | ---: | ---: | ---: |
| 0% | 15,90 | 16,20 | 23,40 |
| 5% | 28,65 | 21,00 | 23,40 |
| 10% | 31,20 | 24,45 | 29,10 |
| 20% | 43,50 | 33,60 | 33,90 |
| 40% | 75,75 | 44,40 | 43,50 |

При 40% потерь P90: repeat **107,1 с**, systematic **49,5 с**, repair-only
**56,4 с**. Выигрыш systematic по медиане — около **1,71×**. Без потерь repeat
немного быстрее; repair-only платит за избыточность даже на чистом канале.
Основной профиль не переключается автоматически: repeat остаётся по умолчанию.

Для burst 0,5/2/5 с медианы systematic — 26,85/28,20/30,30 с; смешанный сценарий
позднего подключения — 34,35 с. Детали и P90 всех режимов сохранены в JSON.
Поле `extra_over_ideal_payload_seconds` показывает задержку сверх идеального числа
пакетов полезных байтов; это не время доставки от гипотетического ACK.

В systematic-расписании source и repair разделены на фазы внутри группы до
8 блоков. Это предотвращает преждевременные repair короткого последнего блока,
пока ещё показываются source длинного. На больших объектах между группами всё
равно присутствуют repair-фазы; замер 128 КиБ не доказывает тот же выигрыш для 10 МиБ.

## CPU, память, подготовка и браузер

Для архива сравнения подготовка бинарного пула:

- systematic: 192 символа / 217 кадров с bootstrap, **0,0101 с**;
- repair-only: 144 символа / 163 кадра, **0,0080 с**.

Это генерация LT-байтов, не QR-матриц. Все 540 пакетных прогонов с синхронной
SQLite заняли **92,02 с wall-clock**. Наблюдавшаяся RSS процесса выросла с
31,79 до 36,74 МиБ; максимум состояния одной попытки — 701 972 байта.
Это выборки, не универсальный верхний предел памяти backend.

[Браузерный прогон](../../benchmarks/fec/browser-2026-09-16.json): зашифрованный
малый объект, два QR, Full HD, 250 мс на слот. 97 уникальных матриц подготовлены
за **11,97 с**, файл матриц 379 961 байт. Скорость генерации около 8 матриц/с;
она существенно ниже скорости подготовки LT-пакетов. Предварительная генерация
устраняет риск истощения очереди во время показа, но увеличивает время до старта.

Поздний старт и периодическое удаление одной позиции при декодировании:
приём **4,703 с**, затем успешная распаковка и точное сравнение исходника.
Воспроизведение завершённого журнала заняло **0,00584 с**. Источник захвата —
PNG headless Chrome, поэтому это не результат mss/VDI. Повторный browser-стенд
И03 подтвердил работоспособность прежнего repeat после изменений общего плеера.

## Проверки и границы

**81 тест прошёл на Windows/Python 3.10.21 и 3.12.10**. Есть [вектор протокола](../../tests/vectors/aqr2-lt-v1.json), бинарные тесты,
случайные потери, несколько блоков, поздняя metadata, дедупликация, конфликт,
CRC/неверная оболочка, заполнение диска, второй писатель, повреждённое состояние,
вытеснение более 8 активных графов и resume. Готовый wheel проекта 0.5.0
проверен вне исходников на Python 3.10: полный LT-приём заканчивается успешно.

Конечный пул ограничен максимумом 3K repair на блок. Новые символы после конца
не генерируются, даже если ещё есть пропуски. Увеличение пула/смена транспорта
требует нового `render` и состояния с новым ID. Архив ограничен 16 МиБ,
LT-матрицы — 128 МиБ; крупный объект требует внешних ресурсов вместо standalone.

На реальном VDI остаются сравнение repeat/LT при 1×1 и 2×1 на 1/10 МиБ,
измерение общей длительности с подготовкой, масштаб и возобновление приёма.
Непрерывный worker/producer не реализован; текущая поставка использует
предусмотренный планом конечный режим. Эти ограничения не скрываются за
результатами симулятора.

## Проверка ресурсов на 10 МиБ

[Исходный отчёт](../../benchmarks/fec/large-storage.json). Взята проверенная
зашифрованная фикстура И04 размером 10 486 749 байт. Приём LT-пакетов, SQLite,
восстановление блоков и проверка SHA-256 завершились за **55,62 с**; воспроизведение
журнала — **1,426 с**. RSS процесса: 22,32 МиБ в начале, наблюдавшийся пик
30,71 МиБ. Все подтверждённые символы сохраняются, включая уже не нужные repair,
поэтому журнал ограничен пулом, но не минимизирован.

Это проверка пакетного слоя и хранилища; QR на 10 МиБ не генерировались и через
VDI не показывались. Ограниченный кэш графов не заменяет измерение памяти браузера
при загрузке большого набора матриц. Большие объекты остаются отдельным сценарием
предстоящего совместного теста.
