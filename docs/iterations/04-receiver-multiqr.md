# И04. Устойчивый приёмник, возобновление и несколько QR

[Общий план](../../IMPLEMENTATION_PLAN.md) · Вход: [И03](03-browser-mono-mvp.md) · Далее: [И05](05-erasure-recovery.md), [И06](06-rgb-qr.md), [И07](07-cimbar.md)

Статус: **реализована и проверена локально; измерения нового профиля на VDI открыты**. Цель — убрать ограничения приёмника по памяти/частоте, сохранить прогресс и использовать площадь Full HD для нескольких независимых кодов.

## Результат

Приём из выбранной области экрана, ограниченная очередь кадров, сохранённые подтверждённые чанки, продолжение после перезапуска и измеренный профиль 2×1. При изменении масштаба или разрешения данные сессии сохраняются.

## Задачи

### 1. Захват и декодирование

- [x] Разделить capture, decode и transport/store. Сначала измерить синхронную реализацию, затем выбрать потоки/процессы по реальному освобождению GIL и затратам копирования.
- [x] Реализовать ROI в координатах захвата и понятный выбор монитора, включая отрицательные координаты второго экрана и масштабирование ОС.
- [x] Использовать очередь на 1–2 свежих снимка как начальную настройку. При отставании отбрасывать старый снимок с отдельным счётчиком, не накапливать задержку.
- [x] Планировать захват по сроку следующего кадра с учётом уже потраченного времени; убрать обязательный дополнительный `sleep(1/fps)` после обработки.
- [x] Читать все QR на снимке либо декодировать известные ячейки отдельно. Проверить bytes-API и доступные параметры закреплённой версии ZXing.
- [x] При устойчивом положении повторно использовать геометрию; после ошибки/перемещения/resize выполнять повторный поиск. Быстрый путь не должен навсегда удерживать устаревший ROI.
- [x] Повторные кадры/области можно пропускать по дешёвому fingerprint только после измерения; разные цветные данные в будущем не должны ошибочно считаться одинаковыми.

### 2. Состояние на диске

- [x] Определить версионированный каталог сессии: принятая metadata, ID/профиль, чанки или spool-файл, индекс полученных частей, статистика и стадия завершения.
- [x] Выбрать простую транзакционную схему, например SQLite-индекс плюс spool. Зафиксировать порядок: сначала надёжная запись байтов, затем фиксация индекса; при восстановлении перепроверять записи, которые могли остаться незавершёнными.
- [x] Подтверждённым на диске считать только сохранённый пакет. При пакетной синхронизации отдельно показывать число принятых и зафиксированных частей; допустимую потерю последних несохранённых частей описать.
- [x] Восстанавливать индекс после аварии, проверять повреждение данных/схемы и сверять параметры сессии с новым потоком. Старую сессию с иными параметрами не смешивать с новой.
- [x] Один владелец записи в сессию; повторный процесс получает понятную ошибку/режим только чтения. Определить правила устаревшей блокировки после аварии.
- [x] Собирать и хешировать архив последовательно с диска, без `join` всех чанков в RAM. Полный архив публиковать атомарно.
- [x] Команды inspect/resume показывают прогресс, пропуски диапазонами, ошибки и стадию. Таймаут/отмена сохраняют состояние; очистка — явное действие по указанной сессии.
- [x] Ограничить размер состояния и проверить свободный диск. Повтор пакета не создаёт новую запись и не увеличивает объём бесконечно.

### 3. Multi-QR и расписание

- [x] Добавить 1×1 и 2×1 в общий плеер. Каждый слот несёт независимый пакет и может приниматься независимо от остальных.
- [x] Для V40 при 5 px и тихой зоне 4 начать с 1850×925 для двух кодов. Дополнительный зазор и управляющая область должны помещаться в фактический viewport.
- [x] Если места недостаточно, выбрать меньшее целое число пикселей/версию/число позиций по профилю. Не сжимать готовую сетку дробным CSS.
- [x] Реализовать синхронное и поочерёдное обновление слотов. Сравнивать их при одинаковом числе новых символов в секунду, отдельно записывая частоту каждого слота.
- [x] Последний неполный набор заполнять определённым повтором/служебным кадром; не выдавать несуществующие индексы или пустой QR за данные.
- [x] Metadata и калибровка получают явное расписание. Повторения/служебные слоты входят в расходы скорости.
- [x] Смена скорости/расположения сохраняет пакетизацию. Если изменяются payload size или транспорт, создаётся новый ID и явно объясняется невозможность продолжить прежнюю пакетную сессию.

### 4. Изменения экрана и диагностика

- [x] При локально видимом resize плеер пересчитывает геометрию и показывает выбранный профиль.
- [x] Если уменьшилось только изображение VDI на хосте, приёмник сообщает об ухудшении и предлагает ручную настройку. Он не отправляет команду отправителю через несуществующий ACK-канал.
- [x] Автоматически восстанавливать поиск после переноса окна/возврата разрешения; продолжать ту же сессию при неизменных пакетах.
- [x] Добавить по слотам capture/decode time, valid/new/duplicate/invalid, время без прогресса, RAM и объём состояния.

## Артефакты реализации

- Receiver pipeline, постоянное хранилище и спецификация его аварийного восстановления.
- Профили 1×1/2×1, два расписания и измерения по одинаковой полезной нагрузке.
- Воспроизводимые снимки/записи синтетического экрана для тестов ROI, нескольких кодов и смены геометрии.

## Проверки и критерии готовности

- [x] Архив около 10 МиБ принимается без роста RAM пропорционально количеству PNG/всех чанков; расход состояния соответствует уникальным данным и индексу.
- [x] Перезапуск на ранней/средней/поздней стадии и после сборки перед паролем продолжает работу. Потерянные незавершённые записи дочитываются; готовые не принимаются заново как новые.
- [x] Повреждённое состояние, нехватка диска, второй писатель и конфликт пакета дают явную ошибку, без порчи пользовательского результата.
- [x] В одном снимке принимаются оба QR; ошибка одной позиции не блокирует другую. Позднее подключение и неполная последняя сетка проходят.
- [x] Full HD, оконный режим, доступные масштабы и переход 4K → 1080p/эквивалентный resize сохраняют прогресс и позволяют закончить передачу.
- [x] Оба расписания измерены; многопозиционный режим имеет точный отчёт о скорости относительно одного QR, даже если выигрыш оказался меньше номинального.

Производительный декодер важен также для RGB: две позиции с тремя слоями могут требовать шесть независимых QR-декодирований одного снимка. И06 использует эти интерфейсы, а не отдельный неуправляемый цикл захвата.

## Подтверждение реализации

[Запуск И04](../usage/iteration-04.md) · [Хранение и восстановление](../specs/receiver-state.md) · [Отчёт](../reports/receiver-multiqr.md).

Галочки обозначают локальную реализацию/проверки: 10 МиБ через пакетный слой и
SQLite; малый зашифрованный объект через изображения браузера; геометрия и
оба расписания в headless Chrome. Реальный VDI И04 ещё не измерен. Проверка
Full HD/1 МиБ, оставшаяся от И03, не закрывается этими результатами.

Решения: SQLite хранит и пакет, и индекс одной транзакцией (отдельный spool не
нужен); ОС освобождает lock после аварии; fingerprint-пропуск не включён без
отдельного выигрыша на цветных данных. Калибровочные кадры RGB появятся в И06,
в текущем монохромном расписании служебные позиции — metadata.
