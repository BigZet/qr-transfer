# И05. Восстановление потерь: repeat и FEC

[Общий план](../../IMPLEMENTATION_PLAN.md) · Вход: [И01](01-core-protocol.md), [И03](03-browser-mono-mvp.md) · Итоговое сравнение использует [И04](04-receiver-multiqr.md)

Статус: **запланировано**. Цель — уменьшить ожидание последних недостающих частей с помощью готового кода восстановления потерянных пакетов.

## Результат

Сопоставлены циклическое повторение и минимум одна подходящая готовая реализация межпакетного FEC. Есть рабочий адаптер, описание совместимости и измерения на синтетических потерях и реальном VDI. Проверка библиотек начинается рано; окончательная настройка — в И08.

## Что именно исправляет FEC

Коррекция внутри QR восстанавливает повреждённый символ. Межпакетный FEC восстанавливает архив, когда отдельные символы совсем не прочитаны. Повреждённый пакет сначала отклоняется по проверкам протокола; FEC получает только валидные символы или факт их отсутствия.

Fountain-подход позволяет посылать дополнительные восстановительные символы без обратного канала. Приёмнику нужно достаточное количество независимых символов; любые произвольные K пакетов не гарантируют восстановление. Повтор того же repair-пакета новой информации не добавляет.

## Задачи

### 1. Проверить кандидатов на совместимость

- [ ] Сопоставить готовый RaptorQ, Wirehair и доступную LT-реализацию по Python 3.10, ОС хоста, способу вызова, лимитам блока/объекта и возможности сохранить состояние.
- [ ] Для каждого кандидата проверить фактическую установку, API encode/decode, зависимости и тест на случайных байтах. Имя пакета в PyPI не подтверждает нужную реализацию.
- [ ] Начать с RaptorQ, если доступна подходящая поставка; при несовместимости перейти к другому готовому варианту с записанной причиной. Не начинать собственную реализацию fountain-алгоритма без измеренной необходимости.
- [ ] Проверить CPU/RAM, объём служебных данных и доступность генерации новых символов в Python или браузере. Совместимость разных библиотек одной схемы подтверждать векторами.
- [ ] Зафиксировать точную версию/commit и формат её параметров. Стандартизованное описание RaptorQ доступно в [RFC 6330](https://www.rfc-editor.org/rfc/rfc6330); привязка к конкретному API остаётся задачей реализации.

### 2. Специфицировать профиль транспорта

- [ ] Оставить AQR2-repeat без изменений; добавить отдельный версионированный FEC-профиль и serializer для выбранной схемы.
- [ ] Описать параметры объекта, разбиение на source blocks, размер символа, block ID, source/repair ID либо seed и параметры библиотеки. Поля не должны иметь двусмысленный смысл между схемами.
- [ ] Учесть выравнивание/дополнение: итоговые байты обрезаются строго по объявленной длине и проверяются SHA-256.
- [ ] Держать bootstrap достаточно маленьким для базового QR и периодически повторять. Описание объекта включить также в восстанавливаемую оболочку, где это возможно; не создавать циклическую зависимость «для декодирования надо уже декодировать metadata».
- [ ] Ограничить число блоков, размер декодера и допустимые параметры до выделения ресурсов. Более широкий диапазон ID не отменяет ресурсных квот.
- [ ] Выбрать расписание source/repair и чередование блоков против серийных потерь. Если backend поддерживает systematic-режим, сравнить его с выдачей только repair.

### 3. Генерация и показ без обратного канала

- [ ] Проверить скорость генерации в символах/с с учётом числа QR/слоёв. Плееру нужен запас готовых кадров, а не номинально быстрый encoder в отдельном микротесте.
- [ ] Реализовать один проверенный путь непрерывной генерации: готовый JS/WASM в worker либо ограниченный producer-буфер Python через доступный маршрут JupyterHub.
- [ ] Запрос браузером следующей порции у собственного JupyterHub — часть отправителя. Он не несёт сведения от хоста о полученных/потерянных пакетах.
- [ ] Если допустима только предварительная подготовка, задать конечный пул repair-символов и явно описать его предел. После исчерпания повторять пул или давать оператору подготовить новую порцию; такой режим не называть бесконечным fountain-потоком.
- [ ] При нехватке генерации удерживать готовый кадр/показывать паузу, учитывать повторы и время. Не отправлять частично созданный символ.
- [ ] Скорость/слоты регулируются вручную на отправителе; автоматическая адаптация может учитывать только локальную производительность и размеры окна.

### 4. Приём и возобновление

- [ ] Принимать source/repair независимо от порядка, отбрасывать идентичные повторы, отслеживать фактический прогресс backend.
- [ ] Сохранять сериализуемое состояние либо журнал валидных символов с параметрами, достаточный для его детерминированного восстановления.
- [ ] Ограничить журнал по документированному лимиту; выбрасывать данные только когда доказано, что они больше не нужны для восстановления/перезапуска. При достижении предела давать явный результат.
- [ ] Изолировать source blocks по ID, сохранять уже восстановленные блоки и проверять весь объект после сборки. Время перезагрузки декодера включать в отдельную метрику.
- [ ] Для FEC прогресс не обещает точное «осталось N чанков», если API этого не доказывает. Показывать принятые символы, восстановленные блоки, расходы и оценку с пометкой.

## План сравнения

1. Один и тот же зашифрованный архив и QR-геометрия; учитывать различный размер заголовка и metadata в полезной скорости.
2. Симулятор: независимые потери 0/5/10/20/40%, серийные пропуски 0,5/2/5 с, дубликаты, перестановка, позднее подключение и отсутствие metadata в начале.
3. Для каждой конфигурации использовать фиксированный набор seed, например 20 независимых трасс. Ограничить общее число показанных символов/время и сохранить незавершённые попытки.
4. Измерить полное время, source/repair-расход, задержку последних частей, CPU/RAM, журнал и время возобновления. Сравнивать при одинаковом бюджете времени/показанных данных.
5. На реальном VDI сравнить лучшие repeat/FEC при 1×1 и 2×1 на 1/10 МиБ; для финальных вариантов — минимум три полных прогона и 30 МиБ в И08.

## Артефакты реализации

- FEC-адаптер, его спецификация и тестовые векторы; процедура установки/сборки.
- Расширение симулятора и отчёт repeat/FEC с исходными трассами и всеми неудачами.
- Описание непрерывного либо конечного режима генерации и воспроизводимого возобновления.

## Проверки и критерии готовности

- [ ] На валидном входе decode возвращает точные байты; повреждённые/несогласованные символы не создают ложного успеха.
- [ ] Работают позднее подключение, несколько блоков, серийные потери, пауза и перезапуск с восстановлением состояния.
- [ ] FEC укладывается в лимиты CPU/RAM/диска и реальную скорость создания визуальных символов.
- [ ] Сравнение показывает, где FEC уменьшает время завершения и где его расходы не оправдываются; основной режим ещё может зависеть от размера файла.
- [ ] Если готовая библиотека не интегрируется, сохранены воспроизводимые ошибки и проверены доступные альтернативы. Repeat остаётся контрольным режимом, а недоступный FEC не выдаётся за реализованный.

Штатный Wirehair внутри libcimbar оценивается в И07. Добавлять поверх него этот FEC-профиль по умолчанию не требуется.
